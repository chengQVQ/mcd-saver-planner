## 📖 一句话介绍

你在 WorkBuddy / 任意 MCP 客户端里说「**深圳宝安，巨无霸套餐，到店，怎么最省**」，
它会自动遍历全渠道、全量优惠券组合，输出 Top3 最低到手价方案，一句话确认即可下单。

---

## 🎯 项目背景与核心价值

### 用户在麦当劳点餐时面临的真实痛点

打开麦当劳 App 想点一份巨无霸，你会遇到：

- **菜单几十项**，套餐与单品混杂，「巨无霸三件套 41 元」和「巨无霸 26.5 元 + 薯条」哪个更划算？
- **优惠券分散在三个体系**：门店券、麦麦省券（需先领取）、积分券，App 里往往只显示「部分可用」
- **不知道能不能叠加**：门店券和麦麦省券同时用会怎样？买张随单购卡到底亏不亏？
- **三渠道价格不明**：到店自取、得来速车道取餐、麦乐送到家，哪个更划算？

结果就是：用户要么随手点一笔（浪费权益），要么在多个页面反复比对（决策成本高）。

### 本项目的解法

把上述决策过程封装成一个**优惠决策引擎**：自然语言输入 → 意图与参数解析 → 全渠道全量券组合遍历 → 服务端真实价格验证 → Top3 方案输出 → 一键下单。

**关键设计取舍：不本地估算优惠金额，而是把 `calculate-price` 作为唯一事实来源。**
即使官方叠加规则变化，引擎依然给出正确结果，只是多几次调用——用少量调用换取 100% 的准确性。

## ✨ 功能亮点

| # | 能力 | 说明 |
| --- | --- | --- |
| 1 | 🧠 **自然语言意图解析** | 识别 6 类意图（指定餐品/预算推荐/活动查询/订单复购/积分兑换/通用），自动抽取餐品、预算、渠道、人数、位置，缺参主动追问 |
| 2 | 🧮 **全量券组合遍历** | 跨类型券叠加规则引擎，遵守「同类型互斥、跨类型可叠加、活动券独立」规则，输出全局最优解 |
| 3 | 📊 **三渠道并行比价** | 到店自取 / 得来速 / 麦乐送并行计算，按 价格 60% + 时间 25% + 距离 15% 加权评分 |
| 4 | 🛒 **智能凑单建议** | 未达满减门槛时推荐最低价凑单品，并用**收益校验**确认凑单真的更便宜才推荐 |
| 5 | ⭐ **积分价值比算法** | 按「券面值 ÷ 所需积分」排序而非所需积分升序，优先消耗临期积分 |
| 6 | 📅 **活动预判决策** | 解析活动文案估算折扣力度，对比当前最优价给出「现在买 / 等活动买」建议 |
| 7 | 🔁 **订单复购** | 读取历史订单，按今天的优惠重新计算最省方案 |
| 8 | ⚡ **一键领券下单** | 自动领券 → 价格二次校验 → 创建订单 → 返回支付链接 |
| 9 | 🛡️ **稳定性保障** | 并行调用、TTL 缓存、指数退避、优雅降级、状态机约束，单轮调用 ≤ 15 次 |

## 🔬 核心算法

### 1. 最优优惠组合遍历

```
1. 并行拉取：门店券 / 麦麦省券 / 用户已持券
2. 券分类打标：门店券组 / 麦麦省券组 / 活动券组 / 积分券组
3. 生成可行组合：
   - 空组合（不用券）永远保留，作为兜底基线
   - 单券组合
   - 跨类型组合（门店券 + 麦麦省券），跳过互斥与活动券
4. 逐个组合调用 calculate-price，以服务端返回为准
5. 组合数超限时按「券金额 + 是否多券叠加」剪枝，控制调用次数
6. 按最终到手价升序取 Top3
```

### 2. 多渠道综合评分

```
价格得分 = min-max 反向归一化(finalPrice)    权重 0.60
时间得分 = min-max 反向归一化(waitTime)      权重 0.25
距离得分 = min-max 反向归一化(distance)      权重 0.15
         （外送渠道固定 0.5，避免与配送时效重复惩罚）

综合得分 = 0.60×价格 + 0.25×时间 + 0.15×距离
```

### 3. 积分价值比

```
价值比 = 券面值 ÷ 所需积分     （单位：元/积分，越大越划算）

例：5元券/500积分=0.0100    12元券/900积分=0.0133 ✅    30元券/3000积分=0.0100
```

按价值比降序而非所需积分升序，才能找到真正的最优解。

### 4. 凑单收益校验

```
凑单后总价 = 当前总价 + 凑单品价格 − 券优惠额
仅当 凑单后总价 < 不用券总价 时才推荐
```

避免出现「为了用券反而多花钱」的负向体验。

## 🛡️ 稳定性与约束

| 约束 | 实现 |
| --- | --- |
| 单轮工具调用 ≤ 15 次 | 组合数上限 12 + 实时计数熔断 |
| 并发 ≤ 10，间隔 ≥ 100ms | `runLimited()` 分批执行 |
| 429 限流 | 指数退避 1s / 2s / 4s，最多 3 次；客户端滑动窗口预检 |
| 401 Token 失效 | 立即终止，不做无意义重试 |
| 缓存 | 菜单/活动 1 小时，用户券/积分 5 分钟 |
| 优雅降级 | 可选能力失败不影响主流程，返回已算结果并标注 |
| 状态机 | 严格流转，禁止跨状态跳转；新需求自动复位 |

## 🔌 与官方 MCP 契约的对齐

开发中通过真实调用麦当劳 MCP Server 发现并处理了几个关键契约细节，详见 [MCP_INTEGRATION.md](./MCP_INTEGRATION.md)：

1. **优惠券绑定在商品项级**——`couponId` 是 `items[]` 内的字段，多券叠加时必须挂到不同商品项
2. **`beCode` 强关联**——得来速/外送/团餐场景必传，代码中统一由 `resolveChannel()` 处理
3. **金额单位不统一**——价格返回「分」，菜单返回「元」，券类字段为「元」，内部统一为「分」
4. **券的满减信息藏在标题里**——`query-store-coupons` 不返回 `threshold`/`discount`，需从 `title` 文案解析
5. **`items` schema 兼容**——同时兼容标准数组、嵌套对象、双层包裹三种形态
